# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Labyrinth Algorithm is a Unity 3D procedural dungeon generation system (Unity 6000.3.22f1 / URP), plus a small playable rogue-like built on top of it to exercise the algorithm. The generator produces seamlessly connected, thematically distinct 3D areas without loading screens. See `README.md` for a full write-up of the algorithm and design rationale — read it before making non-trivial changes to procedural generation code, it documents the *why* behind design choices (e.g. why blueprints exist, why Prim's MST is applied after Delaunay, why entry-point flags are indexed the way they are).

Public demo: https://dev-rygy.itch.io/labyrinth-procedural-generator

## Working in this repo

This is a Unity project — there is no CLI build/test command that doesn't go through the Unity Editor/Test Runner.

- **Open the project**: open the folder in Unity Hub with editor version `6000.3.22f1` (see `ProjectSettings/ProjectVersion.txt`).
- **Tests**: NUnit tests live in `Assets/Tests` (assembly `RyansLibrary.Tests.asmdef`) and run via Unity's Test Runner (Window > General > Test Runner), or `Unity.exe -runTests -testPlatform EditMode/PlayMode -projectPath . -testResults <path>` from the command line for CI-style runs.
- **Editing C# outside Unity**: the `.csproj`/`.sln`/`.slnx` files at the repo root are Unity-generated (regenerated on editor sync) — don't hand-edit them. Use them for IDE navigation/IntelliSense only.
- `Library/`, `Temp/`, `obj/`, `Builds/`, `Logs/`, `UserSettings/` are all git-ignored, regenerated by Unity — never treat their contents as source of truth.
- `.gif` and `.fbx` assets are tracked via Git LFS (`.gitattributes`).

## Assembly / folder layout

Scripts are split across a few asmdefs, not one monolithic assembly:

- `Assets/Scripts/RyansLibrary.Scripts.asmdef` — the main game/algorithm code (everything under `Assets/Scripts/**`).
- `Assets/Input System/RyansLibrary.PlayerControls.asmdef` — input action bindings.
- `Assets/Tests/RyansLibrary.Tests.asmdef` — NUnit tests.
- `Assets/Plugins/Better Hierarchy/**` and `Assets/External Packages/BlueRaja/**` — third-party/vendored plugins (Better Hierarchy editor tool, BlueRaja priority queue used by pathfinding); treat as vendored, avoid modifying in place.

Within `Assets/Scripts/`:

- `Procedural Generation/` — the generator itself (see Architecture below). `Procedural Generation/Blueprint Generation/` holds the blueprint-placement operations.
- `Scriptable Objects/Procedural Generation/` — SO-based config feeding the generator (room sets, generation parameters).
- `Entities/Player`, `Entities/Enemies`, `Entities/Objects` — runtime actors.
- `AI/` — enemy behavior.
- `Weapons/`, `Scriptable Objects/Abilities/` — combat/ability system.
- `Debugging/` — in-game CLI (`ConsoleCommandRegistry`) and runtime gizmo drawing (`IGizmoDrawer`, `RuntimeGizmos`).
- `Camera/`, `Physics/`, `UI/`, `Interfaces/`, `Utility/`, `Editor/` — supporting systems and editor tooling (e.g. `Editor/ReadOnlyDrawer.cs`).

## Architecture: the procedural generator

The generator is staged as a pipeline of discrete, steppable operations rather than one monolithic function — this was a deliberate choice to make an inherently hard-to-debug process (procedural generation bugs are usually semantic, not exceptions) inspectable one step at a time. When touching generation code, preserve this staging rather than collapsing steps back into inline logic.

**Pipeline stages** (each documented in depth in `README.md`):

1. **Blueprints** (`Blueprint.cs`, `MapGenerationContext.cs`) — single-cell marks on a grid (`Vector3Int` position → `Blueprint`) stored in a static dictionary for O(1) lookup/dedup. Each blueprint carries an `Available` flag (excludes it from room parsing) and a 6-element `EntryPointFlags` bool array marking which faces need doorways (index order: +X, -X, +Z, -Z, +Y, -Y — see README "Room Entry Points").
2. **Blueprint Operations** (`BlueprintOperation` abstract base) — assembly-instruction-style units of work with named input/output ports, queued and executed one at a time via `MapGenerationContext.OperationQueue` (a `LinkedList<BlueprintOperation>`). `MapGenerationContext` also acts as shared memory between operations (`Malloc`/`TryGet`/`Contains`/`Remove`, keyed by string memory IDs), mirroring register/memory semantics from assembly.
3. **Blueprint Graph** (`MapGeneratorController.cs`) — hardcoded controller that loads operations into the queue and steps through them (`Advance(stepLength)` / `AdvanceAll()`), driving an `IEnumerator` coroutine (`ExecuteOperations`) that can be paused/resumed for debugging. A future goal (see README "Upcoming Features") is replacing the hardcoded graph with Unity's graph toolkit — don't assume the graph structure is fixed if asked to extend it.
4. **Zones** — bounded regions that own their own rooms/branches; "Connection Zones" intersect bounds with neighboring zones to link them.
5. **Unique + Divergent Blueprint Placement** — unique rooms (fixed or bounds-random) placed per zone before runtime parsing; divergent rooms added afterward purely to give the pathfinding graph more points to work with.
6. **Delaunay Triangulation** (Bowyer-Watson, 3D via tetrahedra) — connects blueprint points into a graph; degenerate/coplanar tetrahedra are avoided by requiring a point on a different floor, or falling back to 2D Delaunay for single-floor zones.
7. **Greedy MST (Prim's)** — trims the Delaunay graph down to a minimum spanning tree, with optional random extra edges reintroduced for loops.
8. **Pathfinding** (A\*) — connects blueprint pairs/graph nodes; heuristic is swappable (Euclidean, Manhattan, Chebyshev, Dijkstra/zero) to control corridor shape.
9. **The Drunkard's Walk** — recursive-with-backtracking random walk placement, still used for optional branch paths (secrets/rewards). Backtracking recurses to the previous blueprint on a placement dead-end rather than aborting the whole path.
10. **Room Parsing** (`Room.cs`, `RoomGenerator.cs`) — final pass matching parsed blueprint shapes to prefab room types (Small 1x1x1, Long 2x1x1, Tall 1x2x1, Big 2x1x2). Handles rotation by permuting `EntryPointFlags` to match the room's new orientation, not just copying them — this is a common source of subtle door-alignment bugs, check the face-index permutation carefully when editing rotation logic. Currently marked "Reworking" in README — expect this area to be less stable than the rest of the pipeline.

**Other systems documented in README, relevant when touched:**

- **Player state machine** (`Entities/Player`) — modeled explicitly as an NFA (states, alphabet, start/final states documented in README). Each state is a class implementing `Enter()` / `Tick(float)` / `Exit()`; `Exit()` must finish before the next state's logic runs. Follow this pattern for new states rather than adding boolean flags to a shared controller.
- **In-game CLI** (`Debugging/ConsoleCommandRegistry.cs`) — commands are `ConsoleCommand` objects (id + description + `Action<string[]>` delegate) registered into a `Dictionary<string, ConsoleCommand>` registry, decoupled so any script can register/unregister (typically on enable/disable). First token of input = command name, rest = args.
